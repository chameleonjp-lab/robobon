# ロボボ リッチブラウザゲーム実装計画書

- 文書版: 1.0
- 作成日: 2026-08-13
- 対象: `chameleonjp-lab/robobo`
- 配信先: GitHub Pages
- 主対象端末: iPhone 17 Pro
- 最小対応画面: 横320 × 縦568 CSSピクセル
- 状態: 実装開始前の基準文書
- 名称状態: 「ロボボ」は作業名。一般公開とロゴ確定の前に名称調査を行う

## 0. 結論

ロボボは、ロボットを直接動かすゲームではない。プレイヤーは「どんな状況で、何をするか」という行動規則を縦に並べる。ロボットはその規則だけを使って45秒間戦う。戦闘後、プレイヤーは失敗した理由を読み、規則や装備を直して再戦する。

面白さの中心は、強い部品を集めることよりも、自分の考えがロボットの動きとして現れ、直した結果が次の戦闘ではっきり変わることに置く。

見た目を豊かにするため、戦闘には立体感のある2Dロボット、光、煙、破片、影、画面の揺れ、音を使う。ただし、本格的な3D化はしない。編集の読みやすさ、戦闘理由の追いやすさ、iPhoneでの安定動作を優先する。「リッチさ」は、絵の量ではなく、判断・動き・音・結果説明がつながることで作る。

## 1. 4つの視点で採用する判断

| 視点 | 最も重視すること | 採用する判断 |
|---|---|---|
| ゲームプロダクトマネージャー | 誰に何を届け、どこまで作れば完成か | 1回3〜5分で「組む・見る・直す」を一巡できる一人用作品として始める。対人戦やサーバーは初版へ入れない |
| ゲームクリエイター | 何を感じる作品にするか | 自分のロボットが命令どおりに動く誇らしさと、予想外の失敗を発見する笑いを両立する |
| ゲームデザイナー | 遊びが理解でき、改善が続くか | 自由配線式の広い盤面ではなく、上から順に読む縦型の規則カードを使う。戦闘後は原因と直し方を結ぶ |
| ゲームシニアエンジニア | 安定して再現・検査・拡張できるか | ルール計算と描画を分ける。同じ設定なら同じ結果になる計算方式を採用する。まず軽い2D描画で測り、不足時だけ描画ライブラリへ替える |

## 2. ゲームプロダクトマネージャー視点

### 2.1 届ける価値

対象は、複雑なプログラム言語を学びたい人に限定しない。「作戦を考えること」「自分のロボットを眺めること」「少し直して結果が変わること」が好きな中学生以上を中心にする。iPhoneを縦に持ち、5〜15分で編集と再戦を数回行う利用場面を基準にする。

この作品が約束する体験は、次の一文にまとめる。

> 操作の速さではなく、自分が作った判断のよさで勝つ。

### 2.2 1回の遊び方

1. 敵とステージを確認する。
2. 機体、武器、補助装置を選ぶ。
3. 行動規則を6〜12枚並べる。
4. 45秒の自動戦闘を見る。
5. 結果画面で、止まった理由・撃てなかった理由・被弾した理由を確認する。
6. 1〜2か所を直して再戦する。

初めての人は90秒以内に最初の戦闘を始められる構成にする。初回は完成済みの規則を渡し、1枚だけ変更して違いを体験させる。

### 2.3 成功の測り方

アカウントや利用状況の外部送信は初版に入れない。最小完成版ではまず5人で大きな迷いを見つけ、公開候補では20人以上で確認する。人数が少ない間は割合だけで結論を出さず、どこで迷ったかという発言も一緒に残す。

| 確認項目 | 最小完成版の早期目標 | 公開候補の目標 |
|---|---:|---:|
| 説明なしで最初の戦闘を終える | 5人中4人以上 | 85%以上 |
| 敗北後に規則を編集して再戦する | 5人中4人以上 | 70%以上 |
| 2戦目で損傷量か生存時間が改善する | 5人中3人以上 | 60%以上 |
| 記録を見て敗因候補を1つ説明できる | 5人中4人以上 | 70%以上 |
| 規則の追加・移動・削除を説明なしで行える | 5人中4人以上 | 80%以上 |
| 敗北から再戦開始までの中央時間 | 90秒以内 | 90秒以内 |
| もう1任務遊びたいと答える | 5人中3人以上 | 70%以上 |

### 2.4 作る範囲

最初に面白さを確かめる小さな完成版を作る。一般に Minimum Viable Product と呼ばれるが、本書では「最小完成版」と書く。

| 項目 | 最小完成版 | 初版1.0 | 初版に入れない |
|---|---|---|---|
| 対戦 | 一人用、1対1 | 一人用、1対1 | オンライン対戦、協力戦、観戦部屋 |
| 機体 | 1機体 | 3機体 | 部位ごとの組み立て、塗装投稿 |
| 装備 | 主武器2、補助1 | 主武器4、補助4 | 課金、抽選入手、部品合成 |
| 規則 | 条件6、行動7、最大8枚 | 条件12、行動12、最大16枚 | 自由なコード入力、広い配線盤面 |
| 敵 | 2種類 | 8種類 | 人が投稿する敵、生成型の敵 |
| ステージ | 1 | 3 | 自動生成、基地占領、生産 |
| 任務 | 3 | 12 | 長編物語、毎日更新 |
| 保存 | 端末内1枠 | 端末内3枠、書き出し・読み込み | アカウント、クラウド同期 |

### 2.5 完成まで変えない柱

- 直接操作を戦闘中に足さない。
- 負けた理由を見せずに、装備の数だけ増やさない。
- 強い部品を得るための繰り返し作業を中心にしない。
- 元作品の名称、機体、画面、音、文章、任務構成を使わず、独自の作品として作る。

### 2.6 名称と権利の公開判定

「ロボボ」は本書と開発中の作業名として使う。一般検索では、任天堂の『星のカービィ ロボボプラネット』と教育用ロボット「Robobo」が確認できる。これだけで使用可否は判断できないが、検索時の混同や名称上の危険は残る。

P0の中で、特許庁が案内する方法に沿ってJ-PlatPatを使い、文字、読み方、類似する呼び方、ゲームソフトやオンライン提供に関係する分野を確認する。結果を `docs/NAME_REVIEW.md` へ残す。問題がはっきりしない場合は、ロゴ制作と一般公開の前に専門家へ確認するか、改名する。

既存作品から借りる範囲は「戦闘前に判断を組み、自動戦闘を観察して改善する」という着想にとどめる。機体、世界、名前、文章、音、画面、任務、数値は新しく作る。

## 3. ゲームクリエイター視点

### 3.1 作品の感情の流れ

1回の戦闘で「期待 → 驚き → 納得 → 改善」を作る。

- 編集中: 「この判断なら避けられるはず」と予想する。
- 戦闘中: 命令が光り、自分の考えが動きへ変わる。
- 結果: 予想外の失敗を、数値だけでなく場面で見つける。
- 再編集: 直す場所が1つ見え、次を試したくなる。

戦闘の派手さは、この流れを隠さない範囲で使う。爆発で何が起きたかわからなくなるなら、爆発を小さくする。

### 3.2 世界と見た目

舞台は、廃棄された宇宙港を再利用した無人機の試験競技場とする。プレイヤーは整備班の指揮者で、現場へ出ずに無人機の判断を設計する。

表現は、暗い金属の競技場に、機体ごとの発光色、警告灯、走査線を重ねる。ロボットは小さくても向きと状態が読める輪郭にする。赤と緑だけで敵味方や良否を区別せず、形、明るさ、記号も変える。

初版の仮称を次のようにする。実装時に商標と類似名称を再確認する。

| 種類 | 仮称 | 役割 |
|---|---|---|
| 軽量機 | スイフト | 速いが壊れやすい。回避規則を学ぶ |
| 標準機 | バランサー | 装備と規則を試しやすい |
| 重装機 | バスティオン | 遅いが耐える。距離管理を学ぶ |
| 競技場 | ドック07 | 遮蔽物なしの基礎戦 |
| 競技場 | コンテナヤード | 壁と射線を学ぶ |
| 競技場 | 冷却炉 | 熱と危険区域を学ぶ |

### 3.3 豊かさを作る演出

戦闘画面は斜め上から見た2Dとし、次の層を重ねる。

- 機体の本体、砲塔、脚、影を別々に動かす。
- 発射光、薬きょう、煙、破片、床の焦げ跡を使う。
- 命中時は0.05〜0.10秒だけ動きを弱め、重さを出す。
- 大きな被弾だけ、ごく短い画面の揺れと色ずれを使う。
- 音は足音、駆動、警告、武器、命中を分け、重要度の低い音を自動で間引く。

動きを減らす設定が有効なときは、画面の揺れ、色ずれ、強い拡大縮小を止める。音を消しても、警告と命中理由は画面でわかるようにする。

### 3.4 音の方針

最初のタップ後にだけ音を開始し、初期状態は音なしとする。設定から効果音と音楽を別々に切り替えられるようにする。

曲は、編集画面では低く一定、戦闘では規則の成功に合わせて層が増え、結果画面では短く収束する。音源を増やす前に、発射、被弾、警告、勝敗の4系統が聞き分けられることを確認する。

## 4. ゲームデザイナー視点

### 4.1 画面構成

| 画面 | 主な役割 | iPhoneでの形 |
|---|---|---|
| ホーム | 続き、任務、設定 | 大きな3ボタン。現在の機体を背景に表示 |
| 任務選択 | 敵、地形、報酬の確認 | 縦カード。敵の得意距離を記号で表示 |
| 格納庫 | 機体と装備の変更 | 上に機体、下に装備カード。数値差を矢印で表示 |
| 作戦編集 | 行動規則の並べ替え | 縦1列。下部に「規則を追加」「試合開始」を固定 |
| 戦闘 | 自動戦闘と命令追跡 | 上側約70%を競技場、下側に実行中の規則と速度 |
| 分析 | 敗因候補と直し方の確認 | 重要な事実3件、時間線、規則別の実行回数 |

横向きや広い画面では、作戦編集を「規則一覧＋説明」の2列にする。縦向きの1列構成を基準にする。

### 4.2 最初の10分

| 時間 | 体験 | 教えること |
|---:|---|---|
| 0〜1分30秒 | 完成済み作戦で初戦 | 自分で操作しなくても戦う |
| 1分30秒〜3分 | 「敵が近い」の距離を変更 | 数値1つで動きが変わる |
| 3〜5分 | 再戦し、実行中の規則を見る | 黄色い規則と機体行動が対応する |
| 5〜7分 | 飛んでくる弾への回避を追加 | 条件と行動の組み合わせ |
| 7〜10分 | 3戦目と分析 | 敗因候補を読み、次の修正を選ぶ |

説明文を先に長く読ませない。操作が必要になった場所で、画面内に1つだけ説明を出す。

### 4.3 規則カードの仕組み

規則は上から順に調べ、条件を満たし、今すぐ実行できる最初の行動を採用する。これを0.1秒ごとに行う。各カードは、次の形に統一する。

> もし［条件］なら［行動］を［対象・方向・時間］で行う

例: 「もし敵が4m以内なら、主武器を敵へ発射する」

規則カードは次の情報を持つ。

| 情報 | 内容 |
|---|---|
| 有効・無効 | 一時的に外して比較できる |
| 条件 | 敵の距離、弾、体力、熱、障害物など |
| 比較 | 未満、以上、あり、なし |
| 行動 | 移動、旋回、射撃、回避、冷却、待機など |
| 詳細 | 距離、方向、継続時間、装備の対象 |
| 優先順位 | 縦の位置。上ほど先に調べる |

ドラッグだけに頼らず、各カードに「上へ」「下へ」を用意する。長押しでつかみ、動かしたときは挿入位置を大きく表示する。間違えて動かした直後は、元へ戻すボタンを出す。

### 4.4 最初に用意する条件と行動

最小完成版では、組み合わせを増やしすぎない。

| 条件6種 | 行動7種 |
|---|---|
| 常に | 敵へ近づく |
| 敵を発見 | 敵から離れる |
| 敵が指定距離以内 | 左右へ回避する |
| 飛来弾を発見 | 敵の方向を向く |
| 主武器を使用可能 | 主武器を撃つ |
| 熱が指定値以上 | 冷却する |
|  | 待機する |

初版1.0で、体力、弾数、障害物、敵の側面、危険区域、補助装置の状態を条件へ追加する。行動には補助武器、盾、短距離加速、遮蔽物への移動、巡回を加える。

### 4.5 間違いを戦闘前に知らせる

開始ボタンを押したとき、次の問題を検査する。

- 常に成立する規則より下にあり、実行されない規則。
- 装備していない武器を使う規則。
- 最後までどの条件にも当てはまらず、長時間止まる可能性。
- 冷却より発射を常に優先し、熱で止まりやすい並び。
- 同じ条件と行動が重なっている規則。

重大な問題だけ開始を止める。弱い作戦は自由に試せるようにし、改善案を強制しない。

### 4.6 戦闘規則

- 1対1、45秒。相手を破壊するか、時間終了時に残り耐久が多い側が勝つ。
- 同率の場合は、与えた損傷、命中数の順に判定し、それも同じなら引き分けとする。
- 戦闘中の直接操作は、停止、速度変更、表示切替だけにする。
- 再生速度は0.5倍、1倍、2倍。初見の任務は1倍で始める。
- 停止中は、規則判断を1回だけ進め、感知範囲、適正距離、弾道を重ねて確認できる。
- ブラウザが隠れたら自動停止し、戻ったときに再開確認を出す。
- 任務では開始条件と乱数の種を固定し、1か所を直した効果を比べられるようにする。自由試験だけは種を選び直せる。

### 4.7 装備の役割

数値が上位の装備を並べるのではなく、規則の組み方が変わる装備を用意する。

| 装備 | 強み | 弱み | 生まれる判断 |
|---|---|---|---|
| パルス砲 | 素直で当てやすい | 中程度の熱 | 距離と冷却の基礎 |
| 散弾砲 | 近距離で強い | 遠距離で弱い | 接近と離脱 |
| 誘導弾 | 方向がずれても追う | 再使用まで長い | 撃つ時機の選択 |
| 貫通砲 | 遠距離で強い | 発射前に止まる | 射線と予測 |
| 偏向盾 | 正面からの被害を減らす | 熱と電力を使う | 向きと守る時機 |
| 短距離加速 | 弾を避けやすい | 連続使用できない | 危険の優先順位 |
| 放熱器 | 熱を下げやすい | 装甲を減らす | 攻撃回数との交換 |
| 修復材 | 一度だけ回復 | 発動中は無防備 | 体力条件の設計 |

### 4.8 戦闘後の分析

結果は「勝ち・負け」だけで終わらせない。自動判定だけで真の敗因を証明したとは扱わず、「敗因候補」として重要な事実を最大3件だけ見せる。

| 原因の例 | 見せる証拠 | 直す入口 |
|---|---|---|
| 敵を見失った | 発見できなかった秒数、該当場面 | 探索・接近規則を開く |
| 射程外で撃とうとした | 実行失敗回数、平均距離 | 射撃条件の距離を開く |
| 熱で武器が止まった | 停止時間、熱の時間線 | 冷却規則を追加する |
| 回避が遅れた | 飛来弾発見から被弾までの時間 | 回避規則を上へ移す |
| 同じ規則だけ使った | 規則ごとの実行回数 | 使われない規則を表示する |

時間線の印を押すと、その3秒前から戦闘を再生する。再生中は該当規則を黄色、成立しなかった理由を短い灰色文で表示する。

提案は「正解」を自動で作らず、「この規則が使われなかった」「この装備はこの距離では届かなかった」という事実を優先する。

### 4.9 任務構成

初版は12任務とし、4章に3任務ずつ置く。

| 章 | 学ぶこと | 最終課題 |
|---|---|---|
| 1. 起動試験 | 発見、接近、射撃 | 距離を保つ敵 |
| 2. 生存試験 | 飛来弾、回避、熱 | 連射して追い込む敵 |
| 3. 地形試験 | 壁、射線、危険区域 | 遮蔽物を使う敵 |
| 4. 適応試験 | 装備交換、優先順位 | 戦い方を途中で変える敵 |

任務の評価は勝敗、残り耐久、使用規則数の3軸とする。速さだけを評価せず、別の作戦でも最高評価を取れる余地を残す。

### 4.10 調整方法

すべての敵作戦をプレイヤーと同じ規則形式で作る。敵だけが特別な判断を使うことを避け、分析画面の説明と検査を共用する。

各装備と敵について、固定された100種類以上の作戦と乱数の組み合わせを自動対戦させる。勝率だけでなく、何もできない時間、同じ行動の連続、平均戦闘時間も見る。強い構成を弱くする前に、対抗する規則が存在し、画面から理解できるかを確認する。

## 5. ゲームシニアエンジニア視点

### 5.1 技術構成

| 役割 | 採用 | 理由 |
|---|---|---|
| 言語 | 厳格設定のTypeScript | 規則、装備、保存データの取り違えを開発時に見つけやすい |
| 開発・出力 | 実装開始時の安定版ViteとNode.js長期サポート版 | 静的な配信ファイルを作り、GitHub Pagesへ置ける。版はロックファイルで固定する |
| 戦闘描画 | 初期はCanvas 2D | 2機の戦闘には十分な可能性が高く、実行時の依存を減らせる |
| 編集・設定 | 通常のHTMLとCSS | 文字、ボタン、縦スクロール、読み上げを扱いやすい |
| 単体検査 | Vitest | 規則実行器と戦闘計算を素早く検査できる |
| ブラウザ検査 | Playwright | WebKit、Chromium、狭い画面、タッチありの操作を自動確認できる |
| 書式と静的確認 | Biome | 書式とよくある誤りを1つの処理で確認できる |
| 配信 | GitHub ActionsからGitHub Pages | `main` に入った検査済みの出力だけを公開できる |

Reactなどの画面全体を管理する枠組み、3Dエンジン、汎用物理計算、外部の状態管理、音の追加ライブラリは初版で使わない。描画は `BattleRenderer` という交換口の内側へ閉じ込める。Canvas 2Dで性能、表現、制作効率のいずれかが実測目標を満たさない場合だけ、PixiJS 8系の実装時安定版へ交換する。交換しても戦闘結果は変えない。

### 5.2 全体の分け方

戦闘の正解を計算する部分は、画面や音を知らない純粋なTypeScriptとして作る。画面は、その計算結果を受け取って描くだけにする。

```text
作戦・装備・乱数の種
        ↓
規則実行器 → 戦闘計算 → 出来事の記録
                         ↙          ↘
                  2D戦闘描画       分析画面・再生
```

この分離により、画面を開かずに何千回も自動対戦できる。見た目を変更しても勝敗計算が変わりにくい。

### 5.3 同じ設定を再現する計算

同じ作戦、装備、敵、乱数の種なら同じ結果になる作りを使う。これは「決定論的シミュレーション」と呼ばれる。

- 戦闘計算は1秒を60回に分けて進める。描画は最大60回とし、遅い端末でも計算の刻みを飛ばさない。
- 規則は1秒に10回評価する。
- 位置、速度、角度、熱、耐久は整数で持ち、毎回の丸め方を固定する。角度と方向は固定された整数の対応表を使う。
- 時刻の取得、端末の描画速度、`Math.random()` を勝敗計算へ使わない。
- 乱数は戦闘開始時の種から作り、使用順を固定する。
- 三角関数や平方根の結果を勝敗計算へ直接使わず、距離の二乗と固定表を使う。
- 円同士と線分の当たり判定を自作し、汎用物理計算は入れない。

再生データは全画面を録画しない。作戦、装備、種、版番号、主な出来事を保存し、同じ戦闘を計算し直す。

### 5.4 規則実行器

1回の判断は、必ず次の順にする。

1. 全機体のセンサー値を同じ時点から作り、1つの記録へ固定する。
2. 上から順に有効な規則を調べる。
3. 条件を満たし、装備・熱・待ち時間の面でも実行可能な最初の行動を選ぶ。
4. 全機体の移動、旋回、武器の希望を確定する。
5. 移動と壁、弾、命中を固定順で処理する。
6. 同じ刻みの損傷をまとめて反映し、片方の処理順だけが有利にならないようにする。
7. 実行した規則、採用理由、不採用理由、主な出来事を記録する。

規則の形式には版番号を付ける。保存データを読み込むときは、古い版を新しい形式へ変換する。ユーザーが書いた文字列を命令として実行する仕組みや `eval` は使わない。

### 5.5 データの形

```ts
type Program = {
  schemaVersion: number
  id: string
  name: string
  rules: Rule[]
}

type Rule = {
  id: string
  enabled: boolean
  condition: Condition
  action: Action
}

type BattleSpec = {
  simulationVersion: string
  seed: number
  arenaId: string
  player: Loadout
  enemy: Loadout
}
```

装備、機体、任務、敵作戦はコードへ散らさず、識別子付きのデータへまとめる。値の単位を名前へ含め、距離、時間、割合の取り違えを防ぐ。

### 5.6 保存

機体、作戦、再生のように形を持つデータは、画面を止めずにまとめて保存できる IndexedDB を使う。設定だけは小さな保存場所である `localStorage` を使う。GitHub Pages上の他ゲームと保存場所の出所が同じになるため、データベース名とすべてのキーへ `robobo` を付ける。保存が拒否された場合にも戦闘はできるようにし、画面上で「この端末には保存できない」と知らせる。

- すべての保存に形式の版番号、戦闘規則の版、更新日時を付ける。
- 保存前に一時データを作り、検査後に入れ替える。
- 読み込み失敗時は壊れた内容を隔離し、初期化の前に書き出しを案内する。
- 作戦はJSONファイルとして書き出し・読み込みできるようにする。
- 読み込むファイルは256KBを上限とし、大きさ、項目数、文字数、識別子、数値範囲を検査する。

### 5.7 描画と性能の目標

| 項目 | 目標 |
|---|---:|
| 通常時 | 60画面更新/秒を目標、30未満が継続しない |
| 戦闘計算 | 1更新あたり2ミリ秒未満を目標 |
| 初回に必要な圧縮済み通信量 | 3MB以下を目標 |
| 圧縮後のJavaScript | 250KB以下を初期目標 |
| 全素材を含む配信量 | 12MB以下を目標 |
| 20分後の使用メモリ | 150MB以下を目標 |
| 同時上限 | 機体2、弾64、演出粒子250、床跡40 |

端末名だけで画質を決めない。最初の短い戦闘で処理時間を測り、高・中・低の3段階を選ぶ。解像度、影、粒子、床跡の順に下げ、戦闘ルールや弾数は変えない。

背景、床、影のように変わらない絵は先に別のCanvasへ描く。弾、煙、火花の入れ物を使い回し、毎回作り直さない。画面密度は最大2倍とし、軽量設定では下げる。Canvas 2Dで目標を満たせずPixiJSへ交換した場合は、WebGLが使えない端末へ対応状況と確認方法を表示する。実験段階の描画方式を初版の必須条件にしない。

### 5.8 iPhone向けの画面と入力

- `viewport-fit=cover` と安全領域の値を使い、画面の丸みや下部バーにボタンを重ねない。
- 主要ボタンの押せる範囲は44 × 44 CSSピクセル以上にする。
- 規則一覧は縦スクロールを許可し、戦闘のキャンバスだけに不要なスクロールを止める。
- タッチ、マウス、ペンを同じ形で受ける Pointer Events を使う。
- 長押しだけでしか使えない機能を作らない。
- 画面の拡大を一律に封じず、編集画面の文字拡大を妨げない。戦闘中の誤操作は戦闘領域だけで防ぐ。
- 1秒に3回を超える点滅を使わず、重要情報は点滅だけで伝えない。

### 5.9 音、停止、更新

ブラウザは利用者の操作前に音を止めることがあるため、開始ボタンを押したときに音の仕組みを作る。音量と消音は保存する。

iPhoneの通常ブラウザでは振動を利用できないため、触覚を必須にしない。対応端末で補助的に使う場合も、光と音のない状態で情報を失わないようにする。

ページが背後へ移った、画面がロックされた、通話が入った場合は戦闘を停止する。復帰時に経過時間を一気に進めない。

ホーム画面へ追加でき、通信がない状態でも再訪できる仕組みは、初版1.0の完成後に検討する。これは Progressive Web App と呼ばれる。追加するときは、古い計算と新しい素材が混ざらないよう、版ごとの保管と「更新して再読み込み」表示を先に設計する。初版の完成条件には含めない。

### 5.10 検査

| 層 | 主な検査 |
|---|---|
| 規則実行器 | 優先順位、境界値、無効規則、装備不足、熱、待ち時間 |
| 戦闘計算 | 移動、衝突、弾、勝敗、時間切れ、同率、固定された再生結果 |
| 自動対戦 | 無限停止、画面外、数値の破損、偏った勝率、10,000戦の完走、WebKitとChromiumの最終値一致 |
| 画面 | 320 × 568、375 × 667、393 × 852、広い画面、縦横変更、安全領域 |
| 操作 | タップ、ドラッグ中断、連打、戻す、音なし、背後から復帰 |
| 利用しやすさ | キーボード、読み上げ用の名前、色以外の区別、動きを減らす設定 |

自動ブラウザ検査は、iPhone風の画面とタッチを再現できるが、実機そのものではない。都度の実機確認は求めず、最小完成版と公開候補の節目でiPhone 17 Proを使って確認する。

規則実行器、戦闘計算、保存データの検査は、条件分岐の90%以上を通ることを目安にする。数字を満たすためだけの検査は作らず、境界値、同時撃破、規則中断、旧保存からの移行を優先する。

### 5.11 GitHub上の自動確認と公開

変更をプルリクエストにすると、GitHub上で次を順に実行する。

1. 依存関係を固定どおりに取得する。
2. 書式、型、未使用コードを調べる。
3. 単体検査と固定再生の照合を行う。
4. 配信用のファイルを作る。
5. WebKitとChromiumで主要な流れを確認する。
6. 圧縮後の大きさが上限を超えていないか調べる。

`main` へ入った同じ内容だけをGitHub Pagesへ公開する。Viteの公開基準パスは `/robobo/` に固定する。公開処理に秘密の鍵を置かない。外部の画像、音、分析サービスを直接読み込まない。

### 5.12 安全性と権利

- 作戦ファイルはデータとして解釈し、JavaScriptとして実行しない。
- 読み込んだ名称は文字として表示し、HTMLとして差し込まない。
- 読み込んだJSONは、許可した項目だけを新しいデータへ写し、未知の項目、有限でない数、不正な範囲を捨てる。
- 外部送信、広告、追跡、アカウント、秘密情報を初版へ入れない。
- `VITE_` から始まる値を含め、配信用コードへ秘密情報を置かない。
- 依存関係はロックファイルで固定し、更新提案を自動で受け、検査後に取り込む。
- GitHub Actionsは検査時を読み取りだけにし、公開処理だけへPagesの書き込み権限を渡す。外部Actionは変更不能な完全なコミット値で固定する。
- GitHub Pagesでは応答見出しを自由に設定できない前提にし、HTMLの `meta` で可能な範囲の外部読み込み制限を設定する。
- 素材ごとに作成者、入手元、利用条件を `THIRD_PARTY_NOTICES.md` へ記録する。
- 元作品の固有名、画像、音、文章、数値表、画面配置を転用しない。似て見える箇所は公開前に独立レビューする。

### 5.13 推奨ファイル構成

```text

├─ docs/
│  ├─ IMPLEMENTATION_PLAN.md
│  ├─ GAME_RULES.md

│  └─ TEST_PLAN.md

│  ├─ ui/             # HTMLの画面部品
│  ├─ game/
│  │  ├─ simulation/  # 戦闘計算
│  │  ├─ program/     # 規則実行器と検査
│  │  ├─ content/     # 機体、装備、任務、敵
│  │  └─ analysis/    # 結果の理由を作る
│  ├─ render/         # 交換可能なCanvas 2D描画
```

## 6. 実装工程

全30作業を8段階で進める。進み具合は `完了数/30` で報告する。各作業は、原則として1つの小さなプルリクエストにする。強く結び付く作業は、理由を記録したうえでまとめてもよい。

### P0 基準作り — 0/30から4/30

| 番号 | 作業 | 完了条件 |
|---|---|---|
| 01 | ゲーム規則、数値単位、データ項目、用語、名称調査 | `GAME_RULES.md`と`NAME_REVIEW.md`だけで境界の答えが決まる |
| 02 | Vite、TypeScript、Canvas 2Dの最小構成 | ローカルとGitHub上で空の画面を作れる |
| 03 | 自動確認とPages公開 | 検査後の`main`だけが公開される |
| 04 | 画面寸法、安全領域、共通色・文字・ボタン | 320 × 568で横にはみ出さない |

### P1 戦闘の計算 — 5/30から9/30

| 番号 | 作業 | 完了条件 |
|---|---|---|
| 05 | 固定時刻と乱数 | 同じ入力100回で同じ結果になる |
| 06 | 機体の移動、旋回、境界、衝突 | 画面外へ出ず、重なり続けない |
| 07 | センサーと規則実行器 | 採用・不採用理由を全判断で記録する |
| 08 | 発射、弾、命中、熱、待ち時間 | 境界値を単体検査で確認する |

ここまでを最小完成版とする。22/30で、面白さの判定を行う。基準を満たさない場合は装備や任務を増やさず、編集・観戦・分析の往復を直す。

## 7. 初版1.0の完成条件

次をすべて満たしたときだけ、内容完成とする。

- 12任務を最初から最後まで進められる。
- 「組む・見る・原因を読む・直す」が各任務で成立する。
- 同じ戦闘指定は、対応する版の中で同じ結果を再生できる。
- 320 × 568からiPhone 17 Proまで、主要ボタンや文字が隠れない。
- 自動検査、自動対戦10,000回、配信用作成、主要ブラウザ検査が成功する。
- 20分連続で遊び、停止、再開、保存、読み込み、音切替に重大な不具合がない。
- 失敗原因の上位3件が、実際の出来事と矛盾しない。
- 通常文字の色の差、44pxの主要操作、色以外の状態表現、動きを減らす設定を確認する。
- 外部送信、秘密情報、未記録の素材、元作品の固有表現がない。
- 初見確認の目標を満たすか、満たせない理由と公開判断を記録する。
- 「ロボボ」の名称調査結果を記録し、公開名として使うか改名するかを決める。

## 8. 主な危険と止め方

| 危険 | 早い兆候 | 対応 |
|---|---|---|
| 編集が難しく、戦闘前に離脱する | 初戦まで90秒を超える | 完成済み作戦から1枚だけ変える導入へ戻す |
| 戦闘が派手だが理由が読めない | 「なぜ負けたかわからない」が増える | 粒子と揺れを減らし、命令表示と3秒前再生を強くする |
| 自動提案が正解を押し付ける | 全員が同じ作戦になる | 事実だけを提示し、修正候補を複数残す |
| 規則が増え、iPhoneで扱えない | 画面移動と誤操作が増える | 初版上限16枚を守り、絞り込みより段階解放を優先する |
| 装備差が思考を上回る | 強い装備だけで勝てる | 数値の上位互換をなくし、対抗規則を用意する |
| 再生結果が端末でずれる | 固定再生の照合値が一致しない | 整数計算と順序を確認し、ずれる版を公開しない |
| iPhoneで熱・メモリ不足になる | 画質低でも30更新/秒を割る | 粒子、影、床跡、解像度を順に下げ、計算は維持する |
| 保存が消える | 保存拒否や破損の報告 | 書き出し・読み込みと破損隔離を先に完成させる |
| 内容追加で完成が延びる | P4前に装備・任務案が増える | 22/30の面白さ判定までは内容追加を止める |

## 9. 実装中の判断方法

仕様を追加するときは、次の順で判断する。

1. 「組む・見る・原因を読む・直す」のどこを良くするかを一文で示す。
2. 初版の完成に必要か、公開後でもよいかを分ける。
3. iPhoneの編集操作と戦闘の見やすさを確認する。
4. 自動検査できる形へ分ける。
5. 完了条件と元に戻す条件を書いてから実装する。

「リッチに見える」という理由だけでは追加しない。遊びの理由を読みやすくし、端末で安定して動く演出を優先する。
