## 0. 結論

ロボボンは、ロボットを直接動かすゲームではない。プレイヤーは「どんな状況で、何をするか」という行動規則を縦に並べる。ロボットはその規則だけを使って15〜45秒間戦う。戦闘後、プレイヤーは観測できた事実と該当場面を読み、規則や装備を直して再戦する。

面白さの中心は、強い部品を集めることよりも、自分の考えがロボットの動きとして現れ、直した結果が次の戦闘ではっきり変わることに置く。

見た目を豊かにするため、戦闘には立体感のある2Dロボット、光、煙、破片、影、画面の揺れ、音を使う。ただし、本格的な3D化はしない。編集の読みやすさ、戦闘理由の追いやすさ、iPhoneでの安定動作を優先する。「リッチさ」は、絵の量ではなく、判断・動き・音・結果説明がつながることで作る。

## 1. 4つの視点で採用する判断

| 視点 | 最も重視すること | 採用する判断 |
|---|---|---|
| ゲームプロダクトマネージャー | 誰に何を届け、どこまで作れば完成か | 1回3〜5分で「組む・見る・直す」を一巡できる一人用作品として始める。対人戦やサーバーは初版へ入れない |
| ゲームクリエイター | 何を感じる作品にするか | 自分のロボットが命令どおりに動く誇らしさと、予想外の失敗を発見する笑いを両立する |
| ゲームデザイナー | 遊びが理解でき、改善が続くか | 自由配線式の広い盤面ではなく、上から順に読む縦型の規則カードを使う。戦闘後は事実、証拠、複数の実験案を結ぶ |
| ゲームシニアエンジニア | 安定して再現・検査・拡張できるか | ルール計算と描画を分ける。同じ設定なら同じ結果になる計算方式を採用する。まず軽い2D描画で測り、不足時だけ描画ライブラリへ替える |

### 1.1 敵対的検証で追加した停止条件

計画を「予定どおり進めるため」ではなく「誤った前提を早く捨てるため」に検証した。次の判定は、日程より優先する。

| 攻撃した前提 | 見つかった破綻 | 追加する判定 | 届かない場合 |
|---|---|---|---|
| 縦型規則だけで十分に深い | 条件と行動の表現力、継続、中断が未証明 | P0で代表4作戦をカードだけで組み、9/30で灰色の縦切り試作を5人が遊ぶ | 内容、保存、本格演出を増やさず規則の最小拡張か中心体験を再設計する |
| 固定した1戦で改善を測ればよい | 1つの数値へ過剰適応し、唯一解になりやすい | 同一条件の試運転と、3つの固定条件を通す認定を分ける | 最高評価と任務構成を作り直す |
| 敗因候補は自動で正しく出せる | 相関を原因と誤認し、攻略を押し付ける恐れがある | 事実を必ず出来事へ結び、証拠不足を正式な結果にする | 自動の原因表現を止め、出来事の閲覧だけに戻す |
| 2Dなら後から性能調整できる | 描画方式の判断が遅いと作り直しが大きい | P0で機体2、弾64、粒子250の負荷試作を3画質で測る | 本格描画前にCanvas 2Dの設計を減らすかPixiJSへ交換する |
| `main`へ入れば公開してよい | 名称・権利確認前に未完成版を一般公開する矛盾がある | P0は配信物を作るだけ。30/30で利用者の明示承認後に初めてPagesを有効化する | 非公開の配信物で検査を続ける |

9/30の早期判定では、機体1、武器1、敵1、競技場1、規則4〜6枚、15〜20秒の戦闘、実行中規則、観測事実2件だけを使う。初見5人中4人が自力で1か所を直して再戦し、4人が動きの変化を説明し、5人全体で少なくとも2種類の異なる修正が出ることを通過条件とする。

## 2. ゲームプロダクトマネージャー視点

### 2.1 届ける価値

対象は、複雑なプログラム言語を学びたい人に限定しない。「作戦を考えること」「自分のロボットを眺めること」「少し直して結果が変わること」が好きな中学生以上を中心にする。iPhoneを縦に持ち、5〜15分で編集と再戦を数回行う利用場面を基準にする。

この作品が約束する体験は、次の一文にまとめる。

> 操作の速さではなく、自分が作った判断のよさで勝つ。

### 2.2 1回の遊び方

1. 敵とステージを確認する。
2. 機体、武器、補助装置を選ぶ。
3. 行動規則を4〜12枚並べる。
4. 15〜45秒の自動戦闘を見る。変更が働いたら途中で記録を残して編集へ戻れる。
5. 結果画面で、止まった理由・撃てなかった理由・被弾した理由を確認する。
6. 1〜2か所を直して再戦する。

初めての人は30秒以内に意味のある二択を行い、60秒以内に最初の短い戦闘を終えられる構成にする。初回は「ほぼ動くが、明確な弱点が1つある」規則を渡し、1枚だけ変更して同じ条件で改善を測る。勝利を強制せず、損傷量、生存時間、命中機会のいずれかが改善すれば学習成功とする。

### 2.3 成功の測り方

アカウントや利用状況の外部送信は初版に入れない。9/30と最小完成版では開発者以外の5人を必須確認者とし、公開候補までの累計20人を目標にする。20人へ届かない場合は割合による公開品質を主張せず、未確認範囲と所有者のリスク受容を記録する。人数が少ない間は割合だけで結論を出さず、どこで迷ったかという発言も一緒に残す。

`TEST_PLAN.md` に匿名ID、端末・OS、ゲーム経験層、所要時間、観察内容、同意、途中離脱と欠測の扱い、再試験か新規試験か、記録の保存期限を定める。割合は人数も併記し、同じ人の再試験を新規参加者として数えない。

| 確認項目 | 最小完成版の早期目標 | 公開候補の目標 |
|---|---:|---:|
| 意味のある最初の入力までの中央時間 | 30秒以内 | 30秒以内 |
| 説明なしで最初の戦闘を終える | 5人中4人以上 | 20人中17人以上 |
| 戦闘後に規則を編集して再戦する | 5人中4人以上 | 20人中14人以上 |
| 変更前の予想と結果を自分の言葉で説明する | 5人中4人以上 | 20人中16人以上 |
| 記録を見て観測事実を1つ説明できる | 5人中4人以上 | 20人中14人以上 |
| 規則の追加・移動・削除を説明なしで行える | 5人中4人以上 | 20人中16人以上 |
| 規則変更から働いた証拠を見るまでの中央時間 | 30秒以内 | 30秒以内 |
| もう1任務遊びたいと答える | 5人中3人以上 | 20人中14人以上 |

### 2.5 完成まで変えない柱

- 直接操作を戦闘中に足さない。
- 負けた理由を見せずに、装備の数だけ増やさない。
- 強い部品を得るための繰り返し作業を中心にしない。
- 元作品の名称、機体、画面、音、文章、任務構成を使わず、独自の作品として作る。

### 2.6 名称と権利の公開判定

「ロボボン」を選定名として使うが、使用可能という法的判断はまだしていない。2026-08-13の一般検索だけでは同一名の有無を網羅できず、近い呼び方の公式製品「ロボホン / RoBoHoN」も存在する。これは競合や権利侵害を意味しないが、聞き間違いと混同の可能性を公開前に確認する理由になる。

P0の中で、特許庁が案内するJ-PlatPatの「称呼（類似検索）」を使い、「ロボボン」「ROBOBON」「Robobon」「ロボホン」「ROBOHON」など近い文字・読み方を、ゲームソフトとオンラインゲーム提供に関係する指定商品・役務について確認する。第9類と第41類を候補にし、実際の商品・役務と類似群を確認してから範囲を確定する。通常検索、アプリストア、ドメイン、5人の聞き間違い・検索到達も補助確認する。

`docs/NAME_REVIEW.md` へ検索日、検索式、区分・商品役務・類似群、候補の登録番号と状態、根拠URLまたは画面、判断者、結論、再確認日を残す。一般検索も補助に使うが、検索結果がないことを安全の証明にしない。

名称判断が曖昧な場合は専門家へ確認するか改名する。`NAME_REVIEW.md` の明示判定、独自制作記録、素材一覧がそろうまで、ロゴ確定、宣伝、GitHub Pagesの一般公開を止める。

既存作品から借りる範囲は「戦闘前に判断を組み、自動戦闘を観察して改善する」という抽象的な着想にとどめる。元作品の画像、音、文章、機体、画面配置、任務構成、数値表を参照素材として持ち込まない。「縦の優先順位規則」「証拠に結び付く分析」「整備班による試験と認定」を独自の3本柱とする。

機体の輪郭、UI、用語、世界、装備、任務、音、数値の作成根拠と「似せない一覧」を `docs/ORIGINALITY_REVIEW.md` に残す。公開候補では制作へ参加していない確認者が比較し、高い類似を1件でも具体的に指摘した場合は公開を止め、差分を再設計する。

## 3. ゲームクリエイター視点

### 3.1 作品の感情の流れ

1回の戦闘で「期待 → 驚き → 納得 → 改善」を作る。

- 編集中: 「この判断なら避けられるはず」と予想する。
- 戦闘中: 命令が光り、自分の考えが動きへ変わる。
- 結果: 予想外の失敗を、数値だけでなく場面で見つける。
- 再編集: 直す場所が1つ見え、次を試したくなる。

戦闘の派手さは、この流れを隠さない範囲で使う。爆発で何が起きたかわからなくなるなら、爆発を小さくする。

### 3.2 世界と見た目

舞台は、廃棄された宇宙港を再利用した無人機の試験競技場とする。プレイヤーは整備班の指揮者で、現場へ出ずに無人機の判断を設計する。

表現は、暗い金属の競技場に、機体ごとの発光色、警告灯、走査線を重ねる。ロボットは小さくても向きと状態が読める輪郭にする。赤と緑だけで敵味方や良否を区別せず、形、明るさ、記号も変える。

初版の仮称を次のようにする。実装時に商標と類似名称を再確認する。

| 種類 | 仮称 | 役割 |
|---|---|---|
| 軽量機 | スイフト | 速いが壊れやすい。回避規則を学ぶ |
| 標準機 | バランサー | 装備と規則を試しやすい |
| 重装機 | バスティオン | 遅いが耐える。距離管理を学ぶ |
| 競技場 | ドック07 | 遮蔽物なしの基礎戦 |
| 競技場 | コンテナヤード | 壁と射線を学ぶ |
| 競技場 | 冷却炉 | 熱と危険区域を学ぶ |

### 3.3 豊かさを作る演出

戦闘画面は斜め上から見た2Dとし、次の層を重ねる。

- 機体の本体、砲塔、脚、影を別々に動かす。
- 発射光、薬きょう、煙、破片、床の焦げ跡を使う。
- 命中時は0.05〜0.10秒だけ動きを弱め、重さを出す。
- 大きな被弾だけ、ごく短い画面の揺れと色ずれを使う。
- 音は足音、駆動、警告、武器、命中を分け、重要度の低い音を自動で間引く。

動きを減らす設定が有効なときは、画面の揺れ、色ずれ、強い拡大縮小を止める。音を消しても、警告と命中理由は画面でわかるようにする。

通常観戦と「事実確認再生」は分ける。事実確認再生では、揺れ、色ずれ、重要度の低い粒子を自動で止め、規則文字の後ろへ不透明な背景を置く。派手さの設定と情報表示の設定を別にし、演出を減らしても弾道、被弾方向、過熱、実行中規則を失わない。

### 3.4 音の方針

最初のタップ後にだけ音を開始し、初期状態は音なしとする。設定から効果音と音楽を別々に切り替えられるようにする。

曲は、編集画面では低く一定、戦闘では規則の成功に合わせて層が増え、結果画面では短く収束する。音源を増やす前に、発射、被弾、警告、勝敗の4系統が聞き分けられることを確認する。

## 4. ゲームデザイナー視点

### 4.1 画面構成

| 画面 | 主な役割 | iPhoneでの形 |
|---|---|---|
| ホーム | 続き、任務、設定 | 大きな3ボタン。現在の機体を背景に表示 |
| 任務選択 | 敵、地形、報酬の確認 | 縦カード。敵の得意距離を記号で表示 |
| 格納庫 | 機体と装備の変更 | 上に機体、下に装備カード。数値差を矢印で表示 |
| 作戦編集 | 行動規則の並べ替え | 縦1列。下部に「規則を追加」「試合開始」を固定 |
| 戦闘 | 自動戦闘と命令追跡 | 上側約70%を競技場、下側に実行中の規則と速度 |
| 分析 | 観測事実と実験案の確認 | 重要な事実3件、証拠の時間線、規則別の実行回数 |

横向きや広い画面では、作戦編集を「規則一覧＋説明」の2列にする。縦向きの1列構成を基準にする。

### 4.2 最初の10分

| 時間 | 体験 | 教えること |
|---:|---|---|
| 0〜30秒 | 「近づく距離」を二択で予想する | 最初から自分の判断を入れる |
| 30秒〜1分 | 15〜20秒の導入戦を見る | 自分で操作せず、規則が動かす |
| 1〜3分 | 実行中規則と予想との差を見る | 上の規則が選ばれ、下が選ばれない理由 |
| 3〜5分 | 1枚を直し、同じ条件で再戦する | 変更と結果を比べる |
| 5〜7分 | 飛来弾への回避を追加する | 条件、優先順位、中断 |
| 7〜10分 | 事実と該当場面から次の実験を選ぶ | 答えではなく証拠から仮説を作る |

説明文を先に長く読ませない。操作が必要になった場所で、画面内に1つだけ説明を出す。20秒を超える必須の受け身区間を作らず、想定外の結果でも進行不能にしない。

### 4.3 規則カードの仕組み

規則は上から順に調べ、条件を満たし、今すぐ実行できる最初の行動を採用する。これを0.1秒ごとに行う。最小完成版は1条件、初版は最大2条件の「かつ」までとし、「または」と入れ子は入れない。各カードは、次の形に統一する。

> もし［条件］なら［行動］を［対象・方向・時間］で行う

例: 「もし敵が4m以内なら、主武器を敵へ発射する」

規則カードは次の情報を持つ。

| 情報 | 内容 |
|---|---|
| 有効・無効 | 一時的に外して比較できる |
| 条件 | 敵の距離、弾、体力、熱、障害物など。初版では最大2つ |
| 比較 | 未満、以上、あり、なし |
| 行動 | 移動、旋回、射撃、回避、冷却、待機など |
| 詳細 | 距離、方向、継続時間、装備の対象 |
| 優先順位 | 縦の位置。上ほど先に調べる |
| 継続と中断 | 行動の最低継続時間、完了条件、上位規則から中断できるか |

ドラッグだけに頼らず、各カードに「上へ」「下へ」を用意する。ドラッグは見える取っ手から通常の移動量を超えた時点で開始し、長押しを条件にしない。動かしている間は挿入位置を大きく表示し、間違えて動かした直後は元へ戻すボタンを出す。

P0では実装前に、最大8枚のカードで「距離を保って射撃」「攻撃を中断して回避し再開」「過熱時だけ冷却し回復後に再開」「壁を避けて射線を作る」の4課題を紙上またはデータ試作する。4課題中3課題を表現でき、うち2課題で構造の異なる作戦が2つ以上成立することを必須にする。届かない場合は、短い状態記憶か行動列のどちらか一方だけを候補に加え、同じ検査をやり直す。

### 4.4 最初に用意する条件と行動

最小完成版では、組み合わせを増やしすぎない。

| 条件6種 | 行動7種 |
|---|---|
| 常に | 敵へ近づく |
| 敵を発見 | 敵から離れる |
| 敵が指定距離以内 | 左右へ回避する |
| 飛来弾を発見 | 敵の方向を向く |
| 主武器を使用可能 | 主武器を撃つ |
| 熱が指定値以上 | 冷却する |
|  | 待機する |

初版1.0で、体力、弾数、障害物、敵の側面、危険区域、補助装置の状態を条件へ追加する。行動には補助武器、盾、短距離加速、遮蔽物への移動、巡回を加える。

### 4.5 間違いを戦闘前に知らせる

開始ボタンを押したとき、次の問題を検査する。

- 常に成立する規則より下にあり、実行されない規則。
- 装備していない武器を使う規則。
- 最後までどの条件にも当てはまらず、長時間止まる可能性。
- 冷却より発射を常に優先し、熱で止まりやすい並び。
- 同じ条件と行動が重なっている規則。
- 閾値の前後で同じ2行動を毎秒4回より多く切り替える可能性。
- 最後に「常に→探索・待機」のような安全な規則がなく、説明のない無行動が続く可能性。

重大な問題だけ開始を止める。弱い作戦は自由に試せるようにし、改善案を強制しない。

### 4.6 戦闘規則

- 1対1。導入任務は15〜20秒、序盤は15〜30秒、後半は最大45秒とする。相手を破壊するか、時間終了時に残り耐久が多い側が勝つ。
- 同率の場合は、与えた損傷、命中数の順に判定し、それも同じなら引き分けとする。
- 戦闘中の直接操作は、停止、速度変更、表示切替だけにする。
- 再生速度は0.5倍、1倍、2倍。初見の任務は1倍で始める。
- 停止中は、規則判断を1回だけ進め、感知範囲、適正距離、弾道を重ねて確認できる。
- 戦闘中はいつでも「ここまでの記録を残して編集へ戻る」を選べる。再生では「次の規則切替」「次の被弾」「次の実行失敗」へ移動できる。
- ブラウザが隠れたら自動停止し、戻ったときに再開確認を出す。
- 「試運転」は開始条件と乱数の種を固定し、1か所を直した効果を比べる。「認定」は開始位置、障害物、敵の攻撃時機が異なる3つの固定条件を使い、過剰適応を防ぐ。通常クリアは1条件、最高評価は3条件の合計で決める。自由試験だけは種を選び直せる。

### 4.7 装備の役割

数値が上位の装備を並べるのではなく、規則の組み方が変わる装備を用意する。

| 装備 | 強み | 弱み | 生まれる判断 |
|---|---|---|---|
| パルス砲 | 素直で当てやすい | 中程度の熱 | 距離と冷却の基礎 |
| 散弾砲 | 近距離で強い | 遠距離で弱い | 接近と離脱 |
| 誘導弾 | 方向がずれても追う | 再使用まで長い | 撃つ時機の選択 |
| 貫通砲 | 遠距離で強い | 発射前に止まる | 射線と予測 |
| 偏向盾 | 正面からの被害を減らす | 熱と電力を使う | 向きと守る時機 |
| 短距離加速 | 弾を避けやすい | 連続使用できない | 危険の優先順位 |
| 放熱器 | 熱を下げやすい | 装甲を減らす | 攻撃回数との交換 |
| 修復材 | 一度だけ回復 | 発動中は無防備 | 体力条件の設計 |

### 4.8 戦闘後の分析

結果は「勝ち・負け」だけで終わらせない。自動判定だけで真の敗因を証明したとは扱わず、「観測した事実」として重要な項目を最大3件だけ見せる。原因と断定せず、証拠が閾値へ届かなければ「判断材料不足」と表示する。

| 観測した事実の例 | 見せる証拠 | 任意で開く実験案 |
|---|---|---|
| 敵を感知していない時間が長い | 秒数、感知範囲、該当場面 | 探索を増やす案と接近条件を変える案 |
| 射撃希望の多くが射程外だった | 失敗回数、距離分布、該当場面 | 射撃距離を変える案と接近方法を変える案 |
| 過熱で武器を使えない時間があった | 停止時間、熱の時間線 | 冷却時機を変える案と装備を変える案 |
| 飛来弾の感知後に被弾した | 感知から被弾までの時間、規則切替 | 優先順位を変える案と回避方向を変える案 |
| 1つの規則へ実行が偏った | 規則ごとの実行時間と不採用理由 | 条件を狭める案と下位規則を見直す案 |

時間線の印を押すと、その3秒前から戦闘を再生する。再生中は該当規則を黄色、成立しなかった理由を短い灰色文で表示する。

実験案を開く前に、プレイヤー自身の仮説を任意選択または短文で残せるようにする。提案は自動編集せず、交換条件の異なる案を2つ以上示す。同じ種の変更前後を並べ、各事実には判定条件と証拠へのリンクを付ける。

分析器は、意図的に状況を作った50戦以上の正解付き検査で、対応する事実の検出率85%以上、誤検出率10%以下を通す。事実確認再生で証拠へ到達できない表示は公開しない。

### 4.9 任務構成

初版必須は8任務とし、品質条件を通った場合だけ4任務を追加する。4章の内容候補は次のとおりとする。

| 章 | 学ぶこと | 最終課題 |
|---|---|---|
| 1. 起動試験 | 発見、接近、射撃 | 距離を保つ敵 |
| 2. 生存試験 | 飛来弾、回避、熱 | 連射して追い込む敵 |
| 3. 地形試験 | 壁、射線、危険区域 | 遮蔽物を使う敵 |
| 4. 適応試験 | 装備交換、優先順位 | 戦い方を途中で変える敵 |

各任務は `CONTENT_CATALOG.md` に「固有の問い」「敵が見せる特徴」「前任務の単純解が失敗する理由」「異なる2つ以上の攻略方針」「目標試行回数」を持つ。数値だけを変えた任務は追加しない。必須8任務の確認で「次も遊びたい」が70%未満なら、追加4任務を作らず既存任務を直す。

任務の評価は勝敗、残り耐久、任務固有の任意目標を使う。規則の数や使った規則の数を得点にしない。同じ不要規則を足しても評価が上がらず、各任務で異なる2系統以上の作戦が最高評価または同等評価を取れるようにする。

### 4.10 調整方法

すべての敵作戦をプレイヤーと同じ規則形式で作る。敵だけが特別な判断を使うことを避け、分析画面の説明と検査を共用する。

各装備と敵について、固定された100種類以上の作戦と乱数の組み合わせを自動対戦させる。勝率だけでなく、何もできない時間、同じ行動の連続、平均戦闘時間も見る。強い構成を弱くする前に、対抗する規則が存在し、画面から理解できるかを確認する。

非導入任務の半数を超えて同じ作戦が最高評価を取る場合は、万能作戦として公開を止める。すべての条件と行動が2任務以上で意味のある選択になり、説明のない無行動が6秒以上続かないことを自動確認する。

## 5. ゲームシニアエンジニア視点

### 5.1 技術構成

| 役割 | 採用 | 理由 |
|---|---|---|
| 言語 | 厳格設定のTypeScript | 規則、装備、保存データの取り違えを開発時に見つけやすい |
| 開発・出力 | 実装開始時の安定版ViteとNode.js長期サポート版 | 静的な配信ファイルを作り、GitHub Pagesへ置ける。版はロックファイルで固定する |
| 戦闘描画 | P0の負荷試作はCanvas 2D | 2機、弾64、粒子250、HUDで性能・視認性・制作時間を測ってから決める |
| 編集・設定 | 通常のHTMLとCSS | 文字、ボタン、縦スクロール、読み上げを扱いやすい |
| 単体検査 | Vitest | 規則実行器と戦闘計算を素早く検査できる |
| ブラウザ検査 | Playwright | WebKit、Chromium、狭い画面、タッチありの操作を自動確認できる |
| 書式と静的確認 | Biome | 書式とよくある誤りを1つの処理で確認できる |
| 配信 | GitHub ActionsからGitHub Pages | 30/30で明示承認された `main` の同一成果物だけを公開できる |

Reactなどの画面全体を管理する枠組み、3Dエンジン、汎用物理計算、外部の状態管理、音の追加ライブラリは初版で使わない。描画は `BattleRenderer` という交換口の内側へ閉じ込め、初期化、破棄、画質変更、コンテキスト喪失からの再構築を契約に含める。

Canvas 2Dで性能、表現、制作効率のいずれかがP0の実測目標を満たさない場合だけ、PixiJS 8系の実装時安定版へ交換する。PixiJSはCanvasの代替ではなくWebGL/WebGPUを使う前提として評価し、採用時はCanvasの低機能表示を残すか、WebGL必須と対応端末を明示する。交換しても戦闘結果は変えない。

### 5.2 全体の分け方

戦闘の正解を計算する部分は、画面や音を知らない純粋なTypeScriptとして作る。画面は、その計算結果を受け取って描くだけにする。

```text
作戦・装備・乱数の種
        ↓
規則実行器 → 戦闘計算 → 出来事の記録
                         ↙          ↘
                  2D戦闘描画       分析画面・再生
```

この分離により、画面を開かずに何千回も自動対戦できる。見た目を変更しても勝敗計算が変わりにくい。

### 5.3 同じ設定を再現する計算

同じ作戦、装備、敵、乱数の種なら同じ結果になる作りを使う。これは「決定論的シミュレーション」と呼ばれる。

- 戦闘計算は1秒を60回に分ける固定刻みとし、ゲーム時間を端末の経過時間から分離する。描画は最大60回とする。
- 規則は1秒に10回評価する。
- 1回の描画で進める計算は最大8刻みに制限する。250ミリ秒を超える遅れ、背後からの復帰、時刻の大きな飛びを検出したら未処理の端末時間を捨てて自動停止し、再開確認を出す。遅れを勝手に早送りせず、勝敗に使う刻みは飛ばさない。
- 位置、速度、角度、熱、耐久は固定小数の整数で持つ。単位倍率、負数を含む除算の丸め、上限・下限、中間値の最大値、同順位時の識別子順を `GAME_RULES.md` へ固定する。すべてを `Number.MAX_SAFE_INTEGER` 内に収め、範囲外は戦闘を停止する不変条件違反として扱う。
- 時刻の取得、端末の描画速度、`Math.random()` を勝敗計算へ使わない。
- 乱数生成法、32ビットの折返し、種の正規化を版として固定する。用途ごとに種、刻み、機体ID、目的、番号から独立した値を作り、規則を1枚変えても無関係な乱数列がずれないようにする。
- 三角関数や平方根の結果を勝敗計算へ直接使わず、距離の二乗と、実行時に生成しない固定表を使う。
- 円同士と線分の当たり判定を自作し、汎用物理計算は入れない。

状態は項目と順序を固定したバイト列へ正規化し、60刻みごとと最終状態の識別値を作る。V8とJavaScriptCoreで固定された1,000戦の識別値、勝敗、主な出来事を照合する。種と期待値の参照表は公開済み版ごとに残す。

再生データは全画面を録画しない。双方の正規化済み作戦、解決済みの装備数値、内容識別値、種、計算版、最終状態識別値、主要な出来事と要約を保存する。対応実行器が残る版だけ再計算し、非対応版は要約だけを表示して新版で黙って再計算しない。

### 5.4 規則実行器

1回の判断は、必ず次の順にする。

1. 全機体のセンサー値を同じ時点から作り、1つの記録へ固定する。
2. 上から順に有効な規則を調べる。
3. 実行中の行動について、最低継続時間、完了条件、実行不能、中断可能性を固定順で判定する。
4. 継続しない場合は、条件を満たし、装備・熱・待ち時間の面でも実行可能な最初の行動を選ぶ。上位の緊急規則だけが中断でき、中断条件はカードに表示する。
5. 全機体の移動、旋回、武器の希望を確定する。
6. 移動と壁、弾、命中を固定順で処理する。
7. 同じ刻みの損傷をまとめて反映し、片方の処理順だけが有利にならないようにする。
8. 実行した規則、継続・完了・中断・不採用の理由、主な出来事を数値コードで記録する。

行動は `starting`、`active`、`completed`、`blocked` の状態を持つ。移動の最低継続時間など機械側の補正を隠さず、カード説明と事実確認再生で見せる。距離、熱、弾数の境界を往復する検査を行い、意図しない毎秒4回を超える切替を許さない。

規則の形式には版番号を付ける。保存データを読み込むときは、古い版を新しい形式へ変換する。ユーザーが書いた文字列を命令として実行する仕組みや `eval` は使わない。

### 5.5 データの形

```ts
type Program = {
  schemaVersion: number
  id: string
  name: string
  rules: Rule[]
}

type Rule = {
  id: string
  enabled: boolean
  conditions: [Condition] | [Condition, Condition]
  action: Action
}

type BattleSpec = {
  simulationVersion: string
  seed: number
  arenaId: string
  player: Loadout
  enemy: Loadout
  contentDigest: string
}
```

装備、機体、任務、敵作戦はコードへ散らさず、識別子付きのデータへまとめる。値の単位を名前へ含め、距離、時間、割合の取り違えを防ぐ。

### 5.6 保存

機体、作戦、再生のように形を持つデータは IndexedDB を使い、設定だけは `localStorage` を使う。表示名と切り離した `APP_STORAGE_ID = "chameleonjp-lab.robobon.v1"` をデータベース名とすべてのキーへ付け、この識別子は表示名を再変更しても変えない。

GitHub Pages上で同じ `github.io` ホストを使う別ページとは保存場所の出所が同じであり、接頭辞は衝突を避けるだけで安全な隔離にはならない。保存内容を秘密として扱わず、読み込むたびに外部ファイルと同じ検査を行う。強い隔離が必要になった時点で専用ドメインを検討する。保存が拒否された場合にも戦闘はできるようにし、画面上で「端末やブラウザの都合で保存は消えることがある」と書き出しを案内する。

現時点ではゲーム実装と一般公開前なので、過去の正式保存データはない前提とし、不要な名称移行コードは作らない。旧試作識別子のデータが実機で見つかった場合だけ、検査、コピー、完了印、旧データ保持の順で一方向移行し、移行検査を追加する。

- すべての保存に形式の版番号、戦闘規則の版、更新日時を付ける。
- 編集は変更ごとに短い待ち時間を置いて自動保存し、戦闘結果は確定時に保存する。終了イベントだけへ依存しない。
- IndexedDBの処理は短いトランザクションに分ける。不変の改訂データと現在位置を1回の `readwrite` で確定し、正常な旧世代を最低1つ残す。
- `versionchange` で古い接続を閉じ、`blocked`、中断、容量不足、入出力失敗を表示する。移行は連番、再実行可能、失敗時巻戻しとし、旧データを書き出せる状態で行う。
- 読み込み失敗時は壊れた内容を隔離し、初期化の前に書き出しを案内する。2タブ更新、保存中の再読込、容量不足、2世代前からの移行を検査する。
- 作戦はJSONファイルとして書き出し・読み込みできるようにする。
- 読み込むファイルは256KBを上限とし、深さ、配列数、規則数、文字数、重複識別子、安全整数の範囲を検査する。`__proto__`、`constructor`、`prototype` を拒否し、許可項目だけを新しい型付きデータへ写す。
- 永続化する再生は1件512KB以下、最新3件までとする。全規則の不採用理由は開発用だけにし、通常は出来事コード、整数値、行動切替、規則別集計を保存する。作戦は容量整理で自動削除しない。

### 5.7 描画と性能の目標

| 項目 | 目標 |
|---|---:|
| iPhone 17 Pro・標準設定 | 最大負荷5分、1倍速で描画間隔p95が16.7ms以下、p99が33.3ms以下 |
| iPhone 11 Pro・軽量設定 | 最大負荷5分、1倍速で30画面更新/秒を目標、27未満が3秒続かない |
| 戦闘計算 | 1刻みp95が2ミリ秒未満を目標 |
| 初回に必要な圧縮済み通信量 | 3MB以下を目標 |
| 圧縮後のJavaScript | 250KB以下を初期目標 |
| 全素材を含む配信量 | 12MB以下を目標 |
| 長時間 | 20分または50戦後に機体、弾、粒子、音、イベント購読数が基準へ戻り、単調増加しない |
| 同時上限 | 機体2、弾64、演出粒子250、床跡40 |

端末名だけで画質を決めない。最初の短い戦闘で処理時間を測り、高・中・低の3段階を選ぶ。解像度、影、粒子、床跡の順に下げ、戦闘ルールや弾数は変えない。測定は端末、OS、Safari版、低電力設定、冷間・再訪、1倍・2倍を記録し、中央値だけでなくp95、p99、50msを超えた描画の割合を残す。

背景、床、影のように変わらない絵は先に別のCanvasへ描く。弾、煙、火花の入れ物を使い回し、毎回作り直さない。画面密度は最大2倍とし、軽量設定では下げる。Safariで自動取得できないメモリ値を必須合否にせず、実機では再読込、クラッシュ、発熱、入力遅延を確認し、自動環境では生存オブジェクトと資源数の増加を測る。

### 5.8 iPhone向けの画面と入力

- `viewport-fit=cover` と安全領域の値を使い、画面の丸みや下部バーにボタンを重ねない。
- 高さは `100svh` を安全な基準とし、対応環境では `100dvh` を使う。固定した `100vh` へ依存せず、アドレスバーの表示・非表示、回転、文字拡大で主要操作が隠れないことを検査する。
- 主要ボタンの押せる範囲は44 × 44 CSSピクセル以上にする。
- 規則一覧は縦スクロールを許可し、戦闘のキャンバスだけに不要なスクロールを止める。
- タッチ、マウス、ペンを同じ形で受ける Pointer Events を使う。
- 長押しだけでしか使えない機能を作らない。
- 画面の拡大を一律に封じず、編集画面の文字拡大を妨げない。戦闘中の誤操作は戦闘領域だけで防ぐ。
- 1秒に3回を超える点滅を使わず、重要情報は点滅だけで伝えない。

### 5.9 音、停止、更新

ブラウザは利用者の操作前に音を止めることがあるため、開始ボタンを押したときに音の仕組みを作る。音量と消音は保存する。

iPhoneの通常ブラウザでは振動を利用できないため、触覚を必須にしない。対応端末で補助的に使う場合も、光と音のない状態で情報を失わないようにする。

`visibilitychange` で `hidden` になった時点を主な停止信号とし、`pagehide` は補助にする。ページ終了時だけの保存には依存しない。ページが背後へ移った、画面がロックされた、通話が入った場合は戦闘を停止し、復帰時に経過時間を一気に進めない。戻ったときは必ず確認待ちにし、戦闘と音を自動再開しない。

`pageshow` の戻る・進むキャッシュ、AudioContextの状態変化、`pointercancel`、回転中のドラッグを扱う。復帰時は未完了ドラッグを元へ戻し、計算ループ、入力購読、音が二重に登録されないことを実機で確認する。

ホーム画面へ追加でき、通信がない状態でも再訪できる仕組みは、初版1.0の完成後に検討する。これは Progressive Web App と呼ばれる。追加するときは、古い計算と新しい素材が混ざらないよう、版ごとの保管と「更新して再読み込み」表示を先に設計する。初版の完成条件には含めない。

### 5.10 検査

| 層 | 主な検査 |
|---|---|
| 規則実行器 | 優先順位、境界値、無効規則、装備不足、熱、待ち時間 |
| 戦闘計算 | 移動、衝突、弾、勝敗、時間切れ、同率、固定された再生結果 |
| 自動対戦 | 無限停止、画面外、非有限値、安全整数違反、偏った勝率、万能作戦、固定状態識別値 |
| 画面 | 320 × 568、375 × 667、393 × 852、広い画面、縦横変更、安全領域、動的なブラウザバー |
| 操作 | タップ、ドラッグ中断、連打、戻す、音なし、背後から復帰 |
| 利用しやすさ | キーボード、読み上げ用の名前、色以外の区別、動きを減らす設定 |

自動ブラウザ検査は、iPhone風の画面とタッチを再現できるが、実機そのものではない。P0の描画方式判定、9/30、最小完成版、公開候補でiPhone 17 Proを使い、軽量設定はiPhone 11 Proで確認する。

規則実行器、戦闘計算、保存データの検査は、条件分岐の90%以上を通ることを目安にする。数字を満たすためだけの検査は作らず、境界値、同時撃破、規則中断、旧保存からの移行を優先する。不具合はS0「保存破壊・安全上の問題」、S1「進行不能・勝敗破損」、S2「回避策のある主要機能不良」、S3「軽微」に分け、公開時はS0とS1を0件、S2は回避策と修正予定を記録する。

### 5.11 GitHub上の自動確認と公開

変更をプルリクエストにすると、GitHub上で10分以内を目標とする軽い検査を順に実行する。

1. 依存関係を固定どおりに取得する。
2. 書式、型、未使用コードを調べる。
3. 単体検査、固定再生100〜1,000戦、状態識別値の照合を行う。
4. 配信用のファイルを作る。
5. WebKitとChromiumで主要な流れを確認する。
6. 圧縮後の大きさが上限を超えていないか調べる。

夜間または公開候補では、自動対戦10,000戦、固定再生1,000戦、広いブラウザ組合せ、長時間検査を行う。失敗時は種、状態識別値、画面記録、Playwright traceを成果物へ残す。月間の実行時間予算を `TEST_PLAN.md` で定め、超過時は夜間検査を止めて必須検査を優先する。

iPhoneだけでも変更を判断できるよう、各プルリクエストのActions Summaryへ検査要約、主要画面の画像、短い操作動画、性能JSON、配信物のコミット値、失敗時の再実行リンクを載せる。PR確認、成果物確認、承認、前版への復旧を1画面5操作以内で行う手順を `RUNBOOK_IOS.md` に記録し、公開候補前に実際に通す。

9/30と14/30の早期試遊は、同じ端末を渡す対面試験または認証された試遊環境を使う。遠隔の外部テスターへURLを渡す必要がある場合は、P0の名称・独自性ゲート通過後に期限付き試遊URLを使い、検索除外が非公開を保証しないことを明記し、終了後に停止する。試遊URLを本番Pages公開の代わりにしない。

P0からP6は、Viteの公開基準パス `/robobon/` で配信物を作り、Actionsの成果物として検査するだけにする。GitHub Pagesは30/30で名称・独自性・完成条件を通し、利用者がPRへ明示承認した後に初めて有効化する。利用可能な場合は `github-pages` 環境へ承認者を設定する。公開ジョブだけへ `pages:write` と `id-token:write` を渡し、検査済みの同じコミットから作った成果物を公開する。公開後は前版へ戻す手順とPagesを停止する手順を `RUNBOOK_IOS.md` に残す。

表示名、リポジトリ名、Vite base、保存ID、manifestの `scope` と `start_url`、将来のキャッシュ名、canonical URL、OG URLの整合を自動検査する。配信物を `/robobon/` の下で開き、すべての要求が成功し、コンソールエラーと旧公開パスが0であることを公開条件にする。

### 5.12 安全性と権利

- 作戦ファイルはデータとして解釈し、JavaScriptとして実行しない。
- 読み込んだ名称は文字として表示し、HTMLとして差し込まない。
- 読み込んだJSONは、許可した項目だけを新しいデータへ写し、未知の項目、有限でない数、不正な範囲を捨てる。
- 外部送信、広告、追跡、アカウント、秘密情報を初版へ入れない。
- `VITE_` から始まる値を含め、配信用コードへ秘密情報を置かない。
- 依存関係はロックファイルで固定し、更新提案を自動で受け、検査後に取り込む。
- GitHub Actionsは検査時を読み取りだけにし、公開処理だけへPagesの書き込み権限を渡す。外部Actionは変更不能な完全なコミット値で固定する。
- GitHub Pagesでは応答見出しを自由に設定できない前提にし、HTMLの `meta` で可能な範囲の外部読み込み制限を設定する。
- 素材ごとに作成者、入手元、利用条件を `THIRD_PARTY_NOTICES.md` へ記録する。
- 元作品の固有名、画像、音、文章、数値表、画面配置を転用しない。似て見える箇所は公開前に独立レビューする。
- `meta` の外部読み込み制限は完全な応答見出しの代わりにならない。`head` の先頭で `default-src 'self'`、`connect-src 'none'`、`object-src 'none'`、`base-uri 'none'` を基準に必要分だけ許可し、残るクリックジャッキングなどの危険を記録する。
- 未信頼コードへ書き込み権限を渡す `pull_request_target` や、不明な成果物を権限付きで扱う構成を使わない。依存関係レビュー、Dependabot、CodeQLの利用可否をP0で確認する。

## 6. 実装工程

全30項目を8段階の「完了節目」として進める。30項目は同じ作業量ではないため、着手前に子作業、成果物、依存、見積り点をIssueへ付け、`完了数/30` と重み付き進捗を併記する。1つの節目は複数の小さなプルリクエストへ分けてよいが、受入条件を通るまで完了数へ足さない。3作業日を超える見込み、または複数の利用者価値を混ぜるプルリクエストは分割する。

各段階の判定で未達だった場合は、最大2回まで原因を1つに絞って改善し、同じ方法で再確認する。2回後も未達なら次段階を始めず、「範囲縮小」「中心方式の再設計」「企画停止」から所有者が選び、理由と残る危険を記録する。例外で進む場合も未達を完了扱いにしない。

## 8. 主な危険と止め方

| 危険 | 早い兆候 | 対応 |
|---|---|---|
| 編集が難しく、戦闘前に離脱する | 意味ある入力まで30秒、導入戦終了まで60秒を超える | ほぼ動く作戦から1枚だけ変える導入へ戻す |
| 中心の面白さを遅く検証する | 9/30前に本格素材や大量内容を作る | 灰色の縦切り試作を先に5人へ試し、未達なら後工程を止める |
| 規則で必要な作戦を表現できない | 代表4作戦のうち2つ以下しか最大8枚で組めない | 状態記憶か行動列の一方だけを試し、再度失敗したら中心方式を再設計する |
| 行動が境界で震える | 同じ2行動を毎秒4回より多く切り替える | 継続・完了・中断を明示し、隠れた補正を画面へ出す |
| 戦闘が派手だが理由が読めない | 「なぜ負けたかわからない」が増える | 粒子と揺れを減らし、命令表示と3秒前再生を強くする |
| 自動提案が正解を押し付ける | 全員が同じ作戦になる | 事実だけを提示し、修正候補を複数残す |
| 規則が増え、iPhoneで扱えない | 画面移動と誤操作が増える | 初版上限12枚を守り、長押しを使わず段階解放を優先する |
| 装備差が思考を上回る | 強い装備だけで勝てる | 数値の上位互換をなくし、対抗規則を用意する |
| 1つの作戦が全任務を解く | 非導入任務の半数超で同じ作戦が最高評価 | 任務の問い、敵の対応、評価条件を作り直す |
| 再生結果が端末でずれる | 固定再生の照合値が一致しない | 整数計算と順序を確認し、ずれる版を公開しない |
| iPhoneで熱・メモリ不足になる | 画質低でも30更新/秒を割る | 粒子、影、床跡、解像度を順に下げ、計算は維持する |
| 保存が消える | 保存拒否や破損の報告 | 書き出し・読み込みと破損隔離を先に完成させる |
| 内容追加で完成が延びる | P4前に装備・任務案が増える | 22/30の面白さ判定までは内容追加を止める |
| 名称や総体表現が混同される | 類似称呼、検索到達失敗、高類似の独立指摘 | ロゴとPages公開を止め、専門家確認か改名・再設計を行う |
| 未完成版を意図せず公開する | P0〜P6でPages deploymentが走る | 公開権限をP7だけへ閉じ、緊急停止手順を検査する |

## 9. 実装中の判断方法

仕様を追加するときは、次の順で判断する。

1. 「組む・見る・原因を読む・直す」のどこを良くするかを一文で示す。
2. 初版の完成に必要か、公開後でもよいかを分ける。
3. iPhoneの編集操作と戦闘の見やすさを確認する。
4. 自動検査できる形へ分ける。
5. 完了条件と元に戻す条件を書いてから実装する。
6. 3作業日を超える見込みなら子作業へ分ける。
7. 名称、独自性、保存互換、公開範囲へ影響する場合は対応文書と停止条件も同じ変更で更新する。

「リッチに見える」という理由だけでは追加しない。遊びの理由を読みやすくし、端末で安定して動く演出を優先する。
