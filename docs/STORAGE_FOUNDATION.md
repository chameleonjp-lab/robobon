# P2-14 作戦保存基盤

## 目的

作戦編集を中断しても、端末の都合で保存できなくても、戦闘そのものは続けられるようにする。端末保存は秘密の保管場所ではなく、JSONファイルと同じ不可信入力として毎回検査する。

## 正規形

`ProgramDocument`（`src/storage.ts`）を作戦の正規形とする。

- `schemaVersion`: 保存形式の版（現在は`1`）
- `formatVersion`: 作戦データ形式の版（現在は`1`）
- `simulationVersion`: 戦闘計算の版（現在は`p1-08`）
- `id`, `name`, `rules`, `updatedAt`: 作戦識別子、表示名、規則、更新日時

保存時と読込み時に同じ正規化・検査を通す。規則は1〜8枚、優先順位は0〜7、条件は1枚あたり2個以下、継続時間は1〜600刻み、IDは許可文字だけとする。`__proto__`、`constructor`、`prototype` は拒否し、未知の値を実行する仕組みや`eval`は持たない。

## 保存先と改訂

第一候補は`IndexedDB`。`programRevisions`へ不変の改訂を保存し、`programCurrent`の現在位置を同じ`readwrite`トランザクションで更新する。自動保存で改訂が増え続けないよう、作戦ごとに直前の正常改訂を最低1件残して古い改訂を整理する。

IndexedDBを開けない環境では`localStorage`、それも使えない場合はメモリ保存へ切り替える。代替保存は品質保証ではなく、戦闘を止めないための退避である。最大3作戦を保持し、保存容量不足・`blocked`・`versionchange`・トランザクション中断は画面へ通知して書出しを案内する。

編集が確定してから500ms後に自動保存する。終了イベントだけには依存しない。保存済み作戦の削除は現在編集中の値を消さず、書出し・読込みは端末保存とは独立した導線にする。

## JSON入出力

JSONは256KB以下に制限する。深さ、配列項目数、文字数、規則数、重複規則ID、安全整数を検査し、正規形へコピーしてから保存する。旧形式（`schemaVersion: 0`）は検査後に版1へ一方向移行する。形式不一致、破損、容量不足、保存枠超過の場合は、現在の作戦と最後の正常保存を切り替えない。

書出しはiPhoneの共有シート／Filesへ渡せるJSONファイルとし、読込みは「Filesで選ぶ → 検査 → 保存 → 編集へ切替」の順に行う。端末・ブラウザの保存は消える可能性があるため、重要な作戦は書出しを使うよう画面に明記する。

## 検査と残課題

`src/storage.test.ts`でJSON往復、旧形式移行、危険キー、上限超過、重複ID、無効作戦、保存枠、正常保存の保持を確認する。CIでは型検査・全単体検査・`/robobon/` build smokeを通す。

P2-14の実機受入は、iPhone Safariで「保存 → 再起動 → JSON書出し → 端末保存削除 → Filesから読込み」を2回成功させること。プライベート閲覧、容量拒否、2タブ更新、途中再読込、保存消去はP2実機記録へ追加し、失敗時も戦闘を開始できることを確認する。
